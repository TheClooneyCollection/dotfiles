# Structure and dependencies

Separate responsibilities and make dependencies, concurrency and domain boundaries explicit.

6. **View model or view state, by one test.** If it changes something, awaits or holds a dependency, it's a view model. If the same input always gives the same output, it's a view state: data plus pure methods. The view model builds the view states; the view only renders them. Swift: `@Observable @MainActor final class TodoListViewModel` builds `nonisolated struct TodoRowState: Equatable`.
7. **Inject capabilities, not logic.** A capability is one function type (`fetchForecast`, `saveItems`); a `Dependencies` record groups them and makes no choices; a consumer takes only the functions it uses, not the record. An interface only when several operations are always swapped together and a second real implementation exists. Conversion, rounding, formatting and sanitising are plain functions, never injected: there is nothing to swap. Swift: `typealias FetchForecast = @Sendable (City) async throws -> Forecast`; a `static func` for the pure part.
8. **Configuration is what deploys change; paths are code.** Base URL, API version and keys live in a configuration value passed inward; endpoint paths and query names are private constants in the endpoint builder. Tests pass `https://example.com` to prove nothing is hard-coded. Swift: `struct APIConfiguration { let baseURL: URL }`; `private enum Path { static let forecast = "v1/forecast" }`.
9. **Say the concurrency contract out loud.** A type that crosses a thread, task or callback boundary declares that it is safe to, even where the compiler would infer it, so an unsafe field fails at the definition rather than at a distant use. Keep the toolchain's defaults until profiling asks for more. Swift: with main-actor default isolation, write `nonisolated` and `: Sendable` on every such type and on its extensions too (nested types and extensions don't inherit it); no `@concurrent` until profiling asks.
10. **Each layer owns its failures, typed.** The client normalises transport, status and decode failures into its own error while retaining necessary diagnostics through boundary logging or necessary error metadata; the repository decides policy (drop a malformed item, fall back to cached data); the view model maps actionable failures to state. Treat intentional cancellation as lifecycle control, not a request failure the user must handle. Swift: a nested `enum Error: Swift.Error` and functions `throws(Error)`; keep cases payload-free unless needed, including for diagnostics, and preserve `Equatable` where useful for `#expect(throws:)`. Choose the diagnostic and cancellation mechanisms at the boundary; neither arbitrary underlying errors reaching the UI, a universal `.cancelled` case, nor a particular logging implementation is required.
11. **Validate where the value is made, then trust it.** A domain initialiser checks ranges (an age of 13 to 120 on a sign-up form); decoding routes through that initialiser, since a synthesised decoder skips it; mappers reject instead of coerce. No re-checks downstream. A separate wire type is optional when the wire shape matches the model one to one and decoding still runs the validating initialiser. Swift: a custom `init(from decoder:)` that calls the throwing `init`; a whole-match regex before `Decimal(string:)`, which reads `"12abc"` as 12.
12. **Precision-bearing values use a decimal type, parsed from strings.** Money is the common case. A price, a dose, a measured weight: anything a user types or a server sends as a string to protect precision. Wire types carry the string; user text is parsed with its locale; the domain holds a decimal, never a binary float; rounding is one explicit domain operation with a named mode. Swift: `Decimal`, `Decimal(string:)`, one `rounded(decimals:mode:)` helper.
13. **Boundary conversion earns its types.** Keep wire-format logic in the network or serialization layer; domain types need not adopt API encoding concerns. Avoid a second enum that mechanically mirrors domain cases solely to serialize them: custom encoding alone is not an independent responsibility. For one bespoke request format, encode in the request DTO. When deliberately choosing a shared multi-type field representation, use a format-shaped value rather than business-shaped cases; this choice needs neither hypothetical reuse nor a universal JSON abstraction. Implement only supported cases needed now, without speculative protocols or type erasure. Swift: either a request DTO's `encode(to:)`, or an `Encodable` wire value with `string`, `array`, `number` and `null` cases. A private domain extension in the network-layer file can convert to that value; the DTO stores it and uses synthesized encoding. Use wire DTO enums when they have an independent responsibility; the format-shaped value is optional.
14. **Make meaning visible at the boundary.** Types, fields, functions and boundaries should reveal what a value means, who owns it and why values travel together, without positional guesswork or reading implementation. Use named values for cohesive multi-value boundary payloads; keep distinct domain operations distinct and domain payloads separate from wire DTOs. Lightweight local cases can use labelled tuples or typealiases; wrap values for meaning, not merely to reduce argument count. Swift: `Submit = @Sendable (AnswerSubmission) async throws -> SessionStep`, with immutable named `answer`, `questionID` and `sessionID` fields, instead of three positional arguments; a separate request DTO owns the wire representation.
15. **Group by responsibility.** Group properties and related methods by their shared job, keeping related methods adjacent rather than sorting solely by mutability or access level. Inside functions, use blank lines between meaningful stages as applicable: preparation, validation, effects, state changes and return or assertions. Preserve cohesive expressions and UI composition; names and structure carry meaning before comments. Swift: within semantic groups, order properties by shorter-to-longer names, alphabetically for ties; align initializer parameter and assignment order with the properties, with no blank lines between initializer parameter groups. Semantic grouping and initialization dependencies take precedence over mechanical sorting; do not force every stage into every function or split cohesive SwiftUI composition.
